# rag-service

一个面向**法律领域语料**的检索增强生成（RAG）服务：从向量库做语义检索、
基于检索材料生成有依据的回答，并为每一次查询留下完整的可观测记录。

> 在这个项目里，**检索质量被当作一等工程问题**：每次查询都会被追踪、打分、计费，
> 因此参数调整可以**用数据说话**，而不是靠直觉。

---

## 1. 功能特性

- **按形态分层检索** —— 语料含多种互补形态（法条、问答对、咨询对话、结构化判例），
  可按形态分别召回后再合并。
- **有依据的生成** —— 模型只依据检索到的材料作答；材料中确实没有的信息，
  明确回答"材料中未提及"，而不是编造。
- **检索参数可调** —— `top_k`、相似度阈值、检索模式（单路 / 多路）均可在运行时
  通过命令行指定，无需改代码。
- **默认可观测** —— 每次查询产生一条结构化 trace，含阶段级延迟分解、token 用量、
  成本估算、检索分数分布与失败捕获。
- **CI 就绪** —— 每次推送都跑 lint 与测试；测试**不依赖网络与真实凭据**，
  因此在任何环境都能通过。

## 2. 架构

```
                ┌──────────────────────────────────────────────┐
   question ───► │  embed（向量化）                              │
                │        │                                     │
                │        ▼                                     │
                │  search（Milvus，余弦相似度，top-k）           │
                │        │                                     │
                │        ▼                                     │
                │  threshold filter（min_score 过滤）           │
                │        │                                     │
                │        ▼                                     │
                │  generate（对话模型 + 有依据的提示词）          │
                └────────┬─────────────────────────────────────┘
                         │
                         ▼
              answer + contexts + trace(JSONL) + log file
```

**两种检索模式**（`--mode`）：

| 模式 | 行为 |
|---|---|
| `single` | 一次 `top_k` 查询，取全局最相似的若干块 |
| `multi` | 按数据形态分多路召回（每形态 `per_form` 条），合并后按分数排序 |

> 为什么默认取向是多路：单路检索存在**跨形态召回失败**的结构性缺陷 ——
> 相似度最高的块往往集中在同一种形态，导致法条、判例等其它形态完全没有进入上下文。
> 实测数据见 [`evals/EVAL_REPORT.md`](evals/EVAL_REPORT.md)。

模块布局：

| 路径 | 职责 |
|---|---|
| `config/settings.py` | 显式路径加载 `.env` + 启动期校验（缺键立即失败）|
| `src/pipeline.py` | 检索流水线：embed → search → filter → generate |
| `src/observe.py` | 日志设置、trace 记录、成本估算、检索 span |
| `scripts/build_index.py` | 建库：语料 → 切分 → 向量 → Milvus（切分与索引参数均可配）|
| `evals/` | 评测集（17 题）＋ 评测脚本 ＋ 评测报告 |
| `experiments/` | 参数实验笔记与收集到的结果 |
| `tests/` | 配置加载与校验的单元测试 |
| `.github/workflows/ci.yml` | lint + test 工作流 |

## 3. 快速开始

```bash
git clone <repository-url>
cd rag-service
python -m venv .venv && source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env        # 然后填入你自己的值
```

查询前需要有一个**可连通且已建好数据**的向量库（见下方 `MILVUS_URL`）。
校验配置并跑一次查询：

```bash
python config/settings.py                      # 启动期校验
python src/pipeline.py -q "你的问题" --top-k 5 --min-score 0.65
python src/pipeline.py -q "你的问题" --mode multi --per-form 3
```

建库（把语料切分、向量化并写入 Milvus）：

```bash
python scripts/build_index.py --corpus ./corpus
python scripts/build_index.py --corpus ./corpus --index-type HNSW \
    --index-params '{"M": 16, "efConstruction": 200}'
```

语料目录下**每个子目录名就是一个数据形态标签**，该标签会写进每块的 `source`
字段（形如 `docs/xxx.md`），供检索侧按形态过滤。

## 4. 配置

所有配置从 `.env` 读取（完整键名见 `.env.example`）。服务在启动时校验每个必需键，
缺键会立即报错并指出缺的是哪一个。

| 变量 | 用途 |
|---|---|
| `API_KEY` | 模型服务的凭据 |
| `BASE_URL` | 对话补全接口地址 |
| `MODEL` | 对话模型标识 |
| `EMBED_BASE_URL` | 向量化接口地址 |
| `EMBED_MODEL` | 向量化模型标识（**必须与建库时所用模型一致**）|
| `MILVUS_URL` | 向量库地址（含协议，如 `http://host:19530`）|

> **关于向量一致性**：查询侧使用的向量化模型必须与**建库时**使用的完全一致。
> 不一致会导致结果接近随机，相似度分数整体崩塌 —— 这类故障详见
> [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md)。

**实验参数留痕**：建库与检索的实验网格声明在
[`config/experiments.yaml`](config/experiments.yaml)。
默认值写在**代码**里（保证仓库 clone 下来即可复现），实验网格另附文件记录，
⛔ 不写入本机路径。

## 5. 语料

支撑本文实测结果的索引约 **22,900 块**，来自一份法律领域语料，包含多种互补形态：

| 形态 | 在回答问题时扮演的角色 |
|---|---|
| 法条 / 长文档 | **法律依据** —— 条文的准确表述 |
| 问答对 | **直接答案** —— 简短结论 |
| 咨询对话 | **用户怎么问** —— 口语化表达 |
| 结构化判例 | **司法实践** —— 法院怎么判 |

同一条问题的不同侧面分属不同形态，因此**跨形态召回**是这个语料下最自然的评测目标。

## 6. 评测与实验

检索质量用**两级证据**衡量：

- **客观层（已实现）**：17 题固化评测集 + 逐题命中判定，
  指标含总体命中率、**分形态命中率**、延迟。见
  [`evals/EVAL_REPORT.md`](evals/EVAL_REPORT.md)。
- **主观层（计划中）**：LLM 打分（相关性 / 忠实度）。

### 已完成的实验（四组配置对比）

| 策略 | 候选数 | 总体命中 | 跨形态 | 最大语料形态 | 延迟均值 |
|---|:--:|:--:|:--:|:--:|:--:|
| 单路 `top_k=5` | 5 | 94.1% | **66.7%** | 100% | 568 ms |
| 多路 `per_form=2` | 8 | 94.1% | 100% | **66.7%** | 351 ms |
| **多路 `per_form=3`** | **12** | **100%** | 100% | 100% | 392 ms |
| 多路 `per_form=5` | 20 | 100% | 100% | 100% | 455 ms |

**核心结论**：

1. 单路检索下**跨形态召回失败**；多路召回修复了它（66.7% → 100%）。
2. 但**候选名额是零和的** —— `per_form=2` 修好了跨形态，却把最大语料形态的
   命中率从 100% 压到 66.7%，总体命中率不变。
3. 把名额增到 12（`per_form=3`）后**两边兼得**，全部命中。
4. 继续增加到 20（`per_form=5`）**没有收益**，只增加延迟 ⇒ `per_form=3` 是收益拐点。

> **实验设计的经验**：参数旋钮（`top_k` / `min_score`）只改变"喂给模型多少上下文"，
> **不改变最佳命中**；改善召回必须动**检索策略**。但改策略又会引入新的**预算问题**，
> 最终仍需用参数收尾。更完整的取舍记录见 [`DESIGN.md`](DESIGN.md)。

实验设计、原始数据与结论写在 [`experiments/tuning_notes.md`](experiments/tuning_notes.md)。

## 7. 可观测性

每次查询产生一条 JSONL trace 和一行日志：

| 字段 | 含义 |
|---|---|
| `trace_id` | 串联日志行、trace 记录与任何堆栈信息 |
| `stage_ms` | 各阶段延迟分解（embed / search / generate）|
| `usage` | 模型返回的 token 计数 |
| `cost_cny` | 该次查询的成本估算 |
| `retrieval` | 分数分布与命中的形态 |
| `status` / `error` | 成功或失败，失败时保留错误信息以便复现 |

**实测性能特征**（52 条 trace，见 `evals/EVAL_REPORT.md` §5）：

| 阶段 | 中位延迟 |
|---|:--:|
| embedding | 366.6 ms |
| **检索** | **30.6 ms** |
| **生成** | **2,897.1 ms** |

⇒ **生成是唯一的主要延迟来源**（约占端到端 85% 以上），检索仅占约 1%。
单次请求成本约 **0.0045 元**。

产物写在 `logs/` 下（**不入版本控制**）。

## 8. 已知限制

- **向量库是外部依赖**：不可达时查询会干净地失败（并留下 trace），不会静默出错。
- **成本估算口径有限**：`cost_cny` 只覆盖**生成阶段**的模型调用，
  **embedding（以及将来的重排）未计入** ⇒ 该数字是**下界**，不是全链路成本。
- **相似度阈值是全局的**：按形态分别设阈值尚未实现（实测表明全局阈值对结构化形态有害）。
- **索引未做调优**：当前使用服务端默认索引。实测检索延迟中位仅 30.6 ms，
  不是端到端瓶颈，因此暂未投入调优。
- **检索延迟的尾部不受控**：中位 30.6 ms 但最大曾达 16.7 s，
  原因之一是旧实现中对多形态做了**串行**检索。这是已知的优化项。
- **尚无在线 Demo、无容器化打包**。
- **语料切分是平铺的**（固定窗口 + 重叠），未按文档结构切分，也未做父子块。
  是否需要改动，取决于是否出现"答案跨块"的实证。
